# 第 1 期实施计划：核心能力

> 设计：`docs/superpowers/specs/2026-09-25-stage-router-design.md` §1–§3、§5
> 前置：第 0 期已完成，六项全部通过，本计划已按其结论调整（见 `2026-09-25-phase0-spikes.md` 的"顺带发现的情况"）。验证用插件 `spikes/spike-plugin.js` 里的注册写法可以直接照抄。
> 完成标准：只写配置就能用——在模型选择器里选 `stage-router/<方案id>`，对话按阶段切换真实模型，重新加载后阶段能恢复。

**做法**

- 纯逻辑放在 `src/engine/` 和 `src/config/`，不依赖 dsh 的运行时，单元测试直接跑。
- 钩子放在 `src/hooks/`，只做接线，靠集成测试覆盖。

**实现**

  - 第 1 期先实现 `tiers` 和 `subagents` 的结构，但不使用它们。
- `defaults.ts`：内置的判断器提示词模板，变量有 `{{current}}`、`{{candidates}}`、`{{recent}}`、`{{message}}`；另有示例方案 `dev-default`。
- `validateScheme(scheme): ConfigIssue[]`，纯函数，每条问题带出错字段的路径（`schemes[0].stages[1].id`）。

**测试**（`test/config.spec.ts`）

- `initialStage` 不合法
- `tiers.default` 不在 `levels` 里
- 判断器配置的部分覆盖能和 `defaultJudge` 正确合并
- 默认示例方案能通过校验

## 任务 3：状态机（`src/engine/transitions.ts`）

**实现**
- `decide(state, event, scheme) → { kind:'stay' } | { kind:'goto', stage } | { kind:'judge', candidates }`。
- 规则：
  - 手动锁定优先；
  - 按顺序匹配，`from:'*'` 是通配；
  - 同一事件命中多条规则、目标又不同时，合起来作为候选阶段，只剩一个候选就直接跳转；
  - `to:'*'` 表示所有阶段都是候选；
  - 会话第一条消息进入 `initialStage`。
- `applyJudgement(state, result, candidates, minConfidence)`：判断失败、置信度不足、或给出的阶段不在候选里，都留在当前阶段。

**测试**（`test/transitions.spec.ts`）：各事件、通配符、多个候选、只剩一个候选、手动锁定、判断失败留在原阶段、第一条消息。

## 任务 4：判断器（`src/engine/judge.ts`）

**实现**
- `renderPrompt(template, vars)`：历史对话摘要取最近 `contextTurns` 轮，每段截断到 800 字。
- `parseJudgement(text)`：
  - 能从代码块里取出 JSON；
  - 缺少 `stage` 或 `confidence` 视为失败；
  - `confidence` 限制在 0 到 1 之间。
- `runJudge(llm, cfg, input, signal)`：
  - 调 `llm.stream({provider, model, system, messages, maxTokens, temperature, signal})`，**不带 `sessionId`**；
  - 用 `BlockAssembler` 收集文字；
  - 超时用 `AbortSignal.any([signal, AbortSignal.timeout(timeoutMs)])`。
- `JudgeCache`：按「会话 ID + 消息 ID」缓存结果。

**测试**（`test/judge.spec.ts`）
- 模板渲染
- 各种 JSON 容错写法
- 超时返回失败
- 同一条消息只调用一次
- 假的 `llm.stream` 收到的参数里没有 `sessionId`

## 任务 5：会话状态（`src/engine/state.ts`）

按第 0 期第 3 项的结论二选一实现。

**首选：用提示消息做持久化载体**
- 模块扩充 `MessageSourceMap`：`'stage-router': {kind:'stage-router', form:'notice', summary, stage, tier?, route, lock?, judge?}`。
- `foldStageState(prev, event)`：纯函数，只处理带 `source.kind==='stage-router'` 的消息事件。
- 投影注册：`{key:'stage-router', stateSchema, init, apply: foldStageState, wire:{viewSchema, view}, stateVersion:1}`，并模块扩充 `SessionProjectionMap`。

**备选：JSON 文件**
- 文件位置 `~/.dsh/stage-router/state.json`，按 sessionId 保存。
- 插件卸载时写盘，会话销毁时清理。

**测试**（`test/state.spec.ts`）
- 折叠一串事件后得到正确的当前阶段、锁定状态、最近一次判断
- 与本插件无关的消息不影响状态
- 首选方案：wire 视图能通过 `viewSchema` 校验

## 任务 6：虚拟服务商（`src/adapter.ts`）

**实现**：`class StageRouterAdapter extends LlmAdapter`

- `resolveModel()`：按设计 §1 声明图片能力；方案不存在时抛出 dsh 的「模型不存在」错误。
- `stream()`：转给初始阶段的真实模型（`ctx.llm.stream`），并写一条 warn 日志。
- 配置变化时（`loader/volatile-update`）调用 `handle.replace(['stage-router'])`。

**测试**（`test/adapter.spec.ts`，用假的 `ctx.llm`）
- 方案列表正确
- 图片能力的推导正确
- `stream()` 会转发

## 任务 7：钩子接线（`src/hooks/*.ts`、`src/index.ts`）

每个钩子一个文件，由 `index.ts` 组装，注册方式照抄 `spikes/spike-plugin.js`。

**第一步**：写一个小工具 `isRouted(agent)`，判断会话是否选用了本插件的方案。无界面模式下没有 `modelSelection` 投影，所以用 agent 服务的 `selectionFor(agent).current`；先在 `spikes/` 里确认这个接口能拿到。

- `hooks/inbox.ts`：注册 `agent/inbox/claimed`。
  - 只处理根 agent，且 `isRouted(agent)` 为真。
  - 执行 `decide`，需要时 `runJudge`，然后 `applyJudgement`。
  - 把结果记为本轮的待定阶段。
- `hooks/planmode.ts`：
  - 进入新阶段时按 `planMode` 调用 `ctx.planMode.set`，并记下这是自己发起的切换，避免来回循环；
  - 在 pre-step 里记下上一步的 `planMode.get(agent).active`：由关变开是 `plan_mode_on`；由开变关，且本轮出现过 `plan-review` 问题（或 `exit_plan_mode` 的结果里有 `approved:true`），是 `plan_approved`，否则是 `plan_mode_off`。
- `hooks/prompt.ts`：注册 `ctx.systemPrompt.section({name:'stage-router:stage', order: getSectionOrder('PLAN_POLICY')+1, text})`，注入当前阶段的提示词。
- `hooks/prestep.ts`：在 `agent/created` 里按 agent 以 `prepend` 注册，在 `agent/disposed` 时注销。
  - 过滤 `source.kind==='model-selection'` 的提示。这一步是必需的：第 2 轮起每一步都会出现这种提示；
  - 处理 `todos_done` 转换；
  - 阶段或模型真的变了，才追加本插件的提示（同时写入持久化状态）。
- `hooks/request.ts`：在插件的根作用域以 `prepend` 注册 `agent/request`（第 0 期第 1 项已验证）。
  - 改写成当前阶段的真实路由；
  - 同一次请求重试时沿用第一次的结果；
  - 阶段模型不可用时按设计 §5 逐级回退。
- 每次路由决策写一条日志：阶段、原因、判断器耗时。

## 任务 8：集成测试（`test/integration/*.spec.ts`）

**测试环境**
- 沿用第 0 期搭好的环境（`spikes/run.mjs` 的做法）：
  - 每轮一个 `dsh headless --json` 进程，从第 2 轮起带 `--session-id`，每轮都是重新加载；
  - 隔离 `DSH_HOME`，设 `DSH_PERMISSION_MODE=danger-full-access`；
  - 测试插件代为批准 `plan-review` 问题。
- 假服务商按脚本返回判断器的 JSON 和助手回复，并记录收到的每个请求。判断器请求和主对话请求靠「有没有 `sessionId`」来区分。
- 注意：系统提示词在 `messages` 里以 `role:'system'` 出现。

**断言**
1. 每一步请求的 provider、model、reasoningEffort 符合预期。
2. 会话历史里没有 `source.kind==='model-selection'` 的提示，只有本插件的阶段提示。
3. 重新加载会话后，阶段能恢复。
4. 计划被批准后，自动进入编码阶段。
5. 判断器超时或返回格式不对时，留在当前阶段。
6. 阶段模型不存在时，按回退链路走，并写 error 日志。

**结果**：`pnpm test` 全绿。然后请你在本地用 `dsh plugin --profile web add .` 安装，完成设计 §8 里的手动验证。
